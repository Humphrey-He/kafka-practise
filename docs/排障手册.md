# Kafka/Sarama 排障手册

这份手册按现象组织，用于后续每个任务 README 链接引用。排障时优先确认三件事：客户端配置、topic/group 状态、broker 端健康。

## 连接不上 broker

常见现象：

- `client has run out of available brokers`
- `dial tcp ... connectex: No connection could be made`
- metadata 获取失败

排查路径：

1. 确认 broker 地址是否能从当前机器访问。
2. 检查 Docker Compose 的 `advertised.listeners`，本地最常见错误是 broker 对外通告了容器内地址。
3. 检查 Kafka 是否已启动完成，不要只看容器 running。
4. 如果开启 SASL/SSL，先区分认证失败、TLS 失败和网络失败。
5. 设置稳定 `ClientID`，从 broker 日志里反查连接行为。

解决要点：

- 本地单机优先暴露 `localhost:9092`。
- 容器之间访问使用 compose service name，宿主机访问使用 localhost 暴露端口。
- 安全连接先用 Kafka CLI 验证，再迁移到 Sarama 配置。

## 生产者发送失败

常见现象：

- 发送超时。
- `LeaderNotAvailable`。
- `NotEnoughReplicas` 或 `NotEnoughReplicasAfterAppend`。
- 异步生产者程序卡住。

排查路径：

1. 检查 topic 是否存在，partition leader 是否正常。
2. 检查 producer 是否消费了 `Errors()` channel。
3. 如果开启 `Return.Successes`，确认也持续消费 `Successes()` channel。
4. 检查 `RequiredAcks` 与 broker/topic 的 `min.insync.replicas` 是否冲突。
5. 检查消息体大小是否超过 producer、broker、topic 限制。

解决要点：

- 异步生产者必须处理成功和失败回执。
- 关键业务使用 `WaitForAll`，并监控 ISR。
- 大消息应谨慎，优先传对象存储地址或拆分消息。

## 消费不到消息

常见现象：

- topic 有数据，但 consumer group 无输出。
- 新启动消费者只消费新消息。
- 指定 group 后看不到历史数据。

排查路径：

1. 查看 group committed offset 是否已经在末尾。
2. 确认 `Consumer.Offsets.Initial` 只在没有提交位移时生效。
3. 确认订阅的 topic 名称和环境是否正确。
4. 检查消费逻辑是否在 `ConsumeClaim` 中阻塞或提前退出。
5. 检查 ACL 是否允许读取 topic 和 group。

解决要点：

- 想重新消费历史数据，可以换 group 或 reset offset。
- 本地调试建议 topic、group、client id 都带任务名。
- consumer group handler 中不要长时间阻塞主消费循环。

## 重复消费

常见原因：

- 处理成功后提交 offset 前进程退出。
- rebalance 发生时未提交最后处理位移。
- 自动提交间隔内进程崩溃。
- 下游写入超时，业务重试后又被 Kafka 重放。

解决要点：

- 默认按至少一次语义设计。
- 处理成功后再 `MarkMessage`/`Commit`。
- 下游写入必须幂等，例如唯一键、事件 ID、去重表。
- 对重复比例打指标，不能只靠日志肉眼观察。

## 消息丢失

常见原因：

- producer 未检查 error。
- `acks=0` 或 `acks=1` 下 broker 故障。
- 消费者处理前提交 offset。
- topic retention 太短，消息过期。
- 副本因子或 ISR 配置不足。

解决要点：

- producer 必须处理发送失败。
- 关键 topic 使用多副本、`acks=all`、合理 `min.insync.replicas`。
- 消费端不要在处理前提交 offset，除非业务明确接受至多一次。
- 对 retention 做容量和时间评估。

## consumer lag 高

常见原因：

- 下游处理慢。
- 分区数不足，无法增加 consumer 并行度。
- 单个 key 热点导致某个分区堆积。
- rebalance 频繁。
- GC、网络、磁盘 IO 抖动。

排查路径：

1. 按 group/topic/partition 观察 lag，而不是只看总量。
2. 对比生产速率和消费处理速率。
3. 查看是否只有少数分区 lag 高。
4. 检查消费者日志里的 rebalance 频率。
5. 检查下游依赖耗时。

解决要点：

- 扩 consumer 前先确认分区数足够。
- 热点 key 需要重新设计分区键。
- 下游慢时先做限流、缓存、重试队列或 DLQ。

## rebalance 频繁

常见原因：

- 消费者实例频繁重启。
- 心跳超时。
- 单批处理太久。
- group 成员数量频繁变化。
- 容器滚动发布没有稳定成员身份。

解决要点：

- 记录 `Setup` 和 `Cleanup` 生命周期日志。
- 调整 session timeout 和 heartbeat interval，但不要盲目调大。
- 长耗时处理异步化，同时保证 offset 提交顺序。
- 稳定部署可使用静态成员 ID。

## SASL/SSL 失败

常见现象：

- TLS handshake failed。
- SASL authentication failed。
- Topic authorization failed。

排查路径：

1. 先区分认证、加密、授权三类错误。
2. 检查本机时间，证书校验依赖时间。
3. 检查 CA、client cert、server name。
4. 检查 SASL mechanism、用户名、密码。
5. 检查 topic、group、transactional ID 的 ACL。

解决要点：

- 不要在生产使用 `InsecureSkipVerify`。
- 密钥和证书路径不要写死。
- ACL 按最小权限授予，并把 client id/group id 规范化。
