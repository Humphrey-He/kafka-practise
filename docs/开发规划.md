# Go + Sarama Kafka 日常开发任务规划

> 说明：用户原文中的 “samara” 按 Go Kafka 生态常用库理解为 **Sarama**。当前建议使用 IBM 维护的模块路径 `github.com/IBM/sarama`。

## 1. 项目定位

本项目用于沉淀 Kafka 日常开发、调试、治理和排障中最常用的一组 Go 小模块。每个模块都应能独立阅读、独立运行、独立验证，并配套说明文档，最终形成一个面向实际开发的 Kafka/Sarama cookbook。

核心目标：

- 用 Go + Sarama 覆盖 Kafka 开发高频场景，而不是只写最小 demo。
- 以任务文件夹组织代码，做到 “一个任务一个入口、一个任务一份说明”。
- 把常见问题的解决要点落到可执行配置、代码策略和验证命令。
- 对 Sarama 能直接实现的能力给出代码；对需要 Kafka 平台、Connect、Flink、JMX、Prometheus 等外部系统的能力给出集成说明和边界。

## 2. 推荐技术栈

- Go：建议使用当前稳定版本，并在 `go.mod` 中固定版本。
- Kafka 客户端：`github.com/IBM/sarama`。
- 本地环境：Docker Compose 启动 Kafka 集群，至少包含 1 个单节点快速环境和 1 个 3 broker 练习环境。
- 配置管理：优先使用 `.env` + YAML/JSON 配置文件，避免把 broker 地址、用户名、密码、证书路径写死在代码里。
- 测试策略：普通逻辑用单元测试；Kafka 行为用本地集群集成测试；生产者/消费者接口可使用 Sarama mocks 做边界测试。
- 观测：代码侧输出结构化日志与指标接口，运维侧用 Kafka CLI、JMX Exporter、Prometheus/Grafana 或 Burrow 验证。

- `internal/common/`：复用配置加载、Sarama client 构造、日志、指标、限流、重试等基础能力。

## 5. 任务清单与细节

### 01-topic-management：主题管理

目标：用 Sarama Admin API 完成主题创建、删除、查看、分区扩展和 topic 配置管理。

建议子任务：

- `create-topic`：创建 topic，配置分区数、副本因子、`retention.ms`、`cleanup.policy`。
- `delete-topic`：删除 topic，说明 broker 侧 `delete.topic.enable` 影响。
- `describe-topic`：查看 topic、partition、leader、replica、ISR。
- `alter-config`：修改保留时间、压缩策略、segment 配置。
- `create-partitions`：扩展分区，说明分区只能增加不能减少。

文档重点：

- 分区数决定 consumer group 最大并行度，但过多分区会增加 broker 元数据、文件句柄和 rebalance 成本。
- `retention.ms` 适合按时间保留；`retention.bytes` 适合按容量控制。
- 日志压缩在 Kafka 里对应 `cleanup.policy=compact`，不是 `log.compaction` 这个客户端参数。
- 删除 topic 是破坏性操作，练习环境中也应加入二次确认或 dry-run。

Sarama 能力边界：

- 可直接使用 `ClusterAdmin` 创建/删除 topic、创建分区、读取/修改配置、查看元数据。
- 分区副本重新分配、leader balance 等更偏运维动作，通常通过 Kafka CLI、Cruise Control 或平台 API 完成。

### 02-producer：生产者

目标：覆盖同步生产者、异步生产者、批量发送、压缩、重试、分区键和序列化。

建议子任务：

- `sync-producer`：发送单条消息并拿到 partition/offset。
- `async-producer`：使用 `Input()`、`Successes()`、`Errors()` channel，并实现优雅关闭。
- `key-partitioning`：相同 key 进入同一分区，说明顺序边界是 “单分区内有序”。
- `batch-and-compression`：调节批量、等待时间、压缩类型。
- `serializer`：封装 JSON、Protobuf 或 Avro 编码器，说明 schema 演进。
- `retry-timeout`：演示重试、超时、错误分类和可观测日志。

文档重点：

- `acks=all` + `min.insync.replicas` 才能形成更强写入可靠性。
- 生产者重试可能造成重复，关键业务需要幂等 producer 或业务幂等键。
- 异步生产者必须消费 `Errors()`；开启 `Return.Successes` 后也必须消费 `Successes()`，否则可能阻塞。
- 批量与压缩提升吞吐，但会牺牲一部分端到端延迟。

Sarama 配置方向：

- `Producer.RequiredAcks` 对应 Java `acks`。
- `Producer.Retry.Max`、`Producer.Retry.Backoff` 对应 retries/backoff 类配置。
- `Producer.Flush.Frequency` 接近 `linger.ms`。
- `Producer.Flush.Bytes`、`Producer.Flush.Messages` 对应批量触发条件。
- `Producer.Compression` 对应 `compression.type`。
- `Producer.Partitioner` 对应 partitioner 策略。

### 03-consumer：消费者

目标：覆盖普通 partition consumer、consumer group、自动/手动位移提交、消费起点、批处理和隔离级别。

建议子任务：

- `partition-consumer`：指定 topic/partition/offset 消费。
- `consumer-group-basic`：实现 `ConsumerGroupHandler` 的 `Setup`、`Cleanup`、`ConsumeClaim`。
- `manual-commit`：处理成功后 `MarkMessage`/`Commit`。
- `auto-commit`：说明适合非关键业务或可接受重复/丢失风险的场景。
- `offset-reset`：配置 oldest/newest 起点。
- `read-committed`：配合事务消息演示 `read_committed`。

文档重点：

- consumer group 是高频生产用法；手动 partition consumer 更适合工具、回放、诊断。
- `MarkMessage` 是标记待提交 offset，不等于一定立即提交。
- 消费处理时间必须小于 group 会话和 poll/rebalance 相关超时，否则可能触发 rebalance。
- 处理逻辑要支持幂等，因为至少一次消费会带来重复。

Sarama 能力边界：

- Sarama consumer group 模型是基于 handler 和 message channel，不是 Java 客户端显式 `poll()` 循环。
- Java 的 `max.poll.records` 在 Sarama 中没有完全等价的一行配置，通常用 `Consumer.Fetch.*`、业务批处理、channel 消费速度和 pause/resume 思路共同控制。

### 04-delivery-semantics：消费一致性

目标：分别实现至少一次、至多一次、精确一次相关方案，并说明外部系统一致性边界。

建议子任务：

- `at-least-once`：处理成功后提交 offset。
- `at-most-once`：处理前提交 offset，演示为什么可能丢消息。
- `idempotent-producer`：启用 producer 幂等。
- `transactional-producer`：使用事务生产消息。
- `consume-process-produce`：消费消息、处理、生产到新 topic，并提交消费位移。
- `external-db-consistency`：说明 DB 写入与 offset 的一致性方案。

文档重点：

- 至少一次是最常见默认实践：不会轻易丢消息，但可能重复。
- 至多一次只适合可丢弃事件，例如非关键统计、采样日志。
- 精确一次通常限定在 Kafka 内部事务链路；跨 DB、HTTP、缓存等外部系统时仍需要幂等或事务协调。
- Kafka 事务需要 producer 端配置事务 ID，consumer 端使用已提交读。

实现建议：

- 先完成 “消费 -> 处理 -> 手动提交”。
- 再完成 “消费 -> 生产新消息 -> 提交 offset” 的事务版本。
- 对外部 DB 示例优先演示 “业务唯一键 + 去重表 + 处理成功后提交 offset”。

### 05-rate-limit-backpressure：消费速率控制与回压

目标：避免消费者压垮下游、避免本地堆积导致 OOM，并形成可调限流策略。

建议子任务：

- `token-bucket`：每秒固定处理 N 条。
- `pause-resume`：下游异常或队列过长时暂停指定分区。
- `bounded-worker-pool`：固定 worker 池处理消息。
- `fetch-tuning`：调整 fetch 大小和等待时间。
- `dlq-retry`：失败消息进入重试 topic 或死信 topic。

文档重点：

- 限流位置可以在消费侧、处理侧、生产侧或 broker quota 侧，不同层级的影响不同。
- pause/resume 要按分区控制，并确保不会超过 group 会话要求。
- worker pool 中 offset 提交要特别小心：不能因为后面的消息先处理完就错误提交前面未完成的 offset。
- 下游保护优先级通常高于盲目追求 lag 归零。

### 06-lag-rebalance：消费滞后与重新分配

目标：计算 lag、识别 rebalance 原因、减少长停顿和频繁重平衡。

建议子任务：

- `lag-calculator`：读取 group offset 与 partition newest offset，计算 lag。
- `rebalance-log`：在 `Setup`/`Cleanup` 打印分区分配变化。
- `static-membership`：配置静态成员 ID，降低滚动发布抖动。
- `slow-consumer-demo`：模拟处理过慢导致 rebalance。
- `partition-balance-report`：输出 topic 分区 leader/replica/ISR 报告。

文档重点：

- lag = partition log end offset - committed offset。
- lag 高不一定是坏事，要结合处理延迟 SLA、下游状态和趋势判断。
- rebalance 常见原因包括进程重启、心跳超时、处理时间过长、成员频繁伸缩、网络抖动。
- 静态成员适合稳定实例身份的容器或虚拟机部署。

Sarama 能力边界：

- 可通过 `Client.GetOffset`、`ClusterAdmin.ListConsumerGroupOffsets` 等能力计算 lag。
- 完整 consumer lag 监控更建议接入 Burrow、Prometheus/JMX 或云厂商监控。

### 07-idempotency-dedup：消息重复与幂等

目标：覆盖生产端幂等、消费端去重、业务幂等写和重复消息观测。

建议子任务：

- `producer-idempotent`：开启 `Producer.Idempotent`。
- `dedup-by-message-id`：用消息 ID 去重。
- `db-unique-key`：用唯一索引保证写入幂等。
- `redis-dedup-window`：用 TTL 去重窗口说明取舍。
- `duplicate-metrics`：统计重复比例和去重命中。

文档重点：

- Kafka 不承诺消费者永远不看见重复消息。
- producer 幂等主要减少生产重试导致的 broker 端重复写入。
- 消费端重复更多来自提交 offset 前宕机、rebalance、下游超时后重试。
- 幂等键应来自业务事实，例如订单号、事件 ID、幂等请求 ID，而不是消费时间。

### 08-durability-retention：数据丢失与持久化

目标：用配置和实验说明 Kafka 写入可靠性、复制、ISR、保留策略和故障风险。

建议子任务：

- `acks-all-min-isr`：验证 `acks=all` 与 `min.insync.replicas`。
- `replication-factor`：创建多副本 topic。
- `retention-policy`：按时间/容量清理消息。
- `compact-topic`：压缩 topic 保存同 key 最新值。
- `broker-failure-lab`：本地 3 broker 环境模拟 broker 下线。

文档重点：

- `replication.factor >= 3` 是生产常见建议，但还要结合机架感知、磁盘、网络和预算。
- `min.insync.replicas` 只有在 producer `acks=all` 时才能发挥写入保护作用。
- ISR 缩小时仍继续写入可能降低可靠性。
- `log.flush.*` 强行刷盘会影响性能，通常依赖操作系统页缓存和副本复制机制。

### 09-throughput-latency：延迟波动与吞吐优化

目标：通过配置矩阵和压测脚本理解吞吐、延迟、CPU、网络、磁盘之间的取舍。

建议子任务：

- `producer-benchmark`：不同 batch、linger、compression 组合对比。
- `consumer-batch-processing`：批处理大小对吞吐和延迟影响。
- `partition-parallelism`：分区数与 consumer 实例数关系。
- `compression-compare`：none/snappy/gzip/lz4/zstd 对比。
- `latency-histogram`：输出 P50/P95/P99。

文档重点：

- 低延迟通常要求小批量、低 linger、快速 flush；高吞吐通常要求批量、压缩和更高并行度。
- 增加分区可以提升并行度，但也会增加 rebalance、文件和元数据成本。
- 压缩能减少网络和磁盘占用，但会增加 CPU 消耗。
- benchmark 必须记录环境，否则结果不可比较。

### 10-monitoring-ops：监控与运维

目标：提供开发侧可落地的健康检查、元数据巡检、lag 输出、ISR 检查和指标暴露。

建议子任务：

- `metadata-health`：检查 broker、topic、partition leader、ISR。
- `consumer-lag-exporter`：输出 group lag。
- `producer-metrics`：统计发送成功、失败、重试、延迟。
- `consumer-metrics`：统计处理耗时、提交延迟、错误率。
- `ops-checklist`：形成日常巡检清单。

文档重点：

- Broker/Topic/Partition 健康包括 leader 是否存在、ISR 是否完整、离线分区、under-replicated partition。
- consumer lag 要分 topic、partition、group 观察。
- GC、磁盘 IO、网络抖动和下游耗时都会反映到 Kafka 指标。
- 代码内指标只能补充业务视角，不能替代 broker/JMX 层监控。

Sarama 能力边界：

- 可读取元数据、offset、consumer group 信息并输出自定义指标。
- Broker GC、磁盘、网络、请求队列等指标来自 Kafka/JVM/JMX 或基础设施监控，不是 Sarama 客户端直接提供。

### 11-pipeline-integration：数据管道

目标：说明 Go/Sarama 在数据管道中的位置，并给出 source/sink 型小模块。

建议子任务：

- `file-source-to-kafka`：读取本地文件写入 topic。
- `http-source-to-kafka`：HTTP 接收事件写入 topic。
- `kafka-to-file-sink`：消费 topic 写入文件。
- `kafka-to-db-sink`：消费 topic 写入数据库，强调幂等。
- `connect-notes`：Kafka Connect source/sink connector 说明。
- `streaming-notes`：Kafka Streams、Flink、Spark 的适用边界说明。

文档重点：

- Sarama 适合写自定义轻量 source/sink、业务服务内嵌生产/消费。
- Kafka Connect 更适合标准系统间搬运，例如 MySQL、Elasticsearch、S3、ClickHouse。
- Kafka Streams 是 JVM 生态；Go 服务通常不直接使用 Kafka Streams API。
- Flink/Spark 更适合状态计算、窗口聚合、复杂 ETL 和大规模流处理。

### 12-security-acl-quota：安全、认证、权限与配额

目标：覆盖 SASL/SSL 连接、证书、ACL 诊断、客户端身份和 quota 说明。

建议子任务：

- `sasl-plain`：用户名密码连接。
- `sasl-scram`：SCRAM 连接。
- `tls-client`：TLS 证书连接。
- `acl-checklist`：权限不足排查清单。
- `quota-notes`：producer/consumer/client quota 说明与验证方式。
- `audit-log-notes`：审计日志字段和排查思路。

文档重点：

- 认证失败和授权失败是两类问题：前者是 “你是谁”，后者是 “你能做什么”。
- TLS 问题常见于证书链、域名校验、过期时间和本地时间不同步。
- ACL 应按最小权限给 topic、group、transactional ID、cluster action。
- 配额通常由 broker 或平台配置，Go 客户端主要负责设置稳定的 client id 和观测限流错误。

### 13-local-debug-testing：开发环境与本地调试

目标：让本地环境尽量可复现生产问题，并提供测试工具和排障流程。

建议子任务：

- `docker-compose-single`：单节点 Kafka 快速启动。
- `docker-compose-cluster`：3 broker 集群，支持副本和 ISR 练习。
- `mock-producer-consumer`：Sarama mocks 单元测试。
- `integration-test`：本地 Kafka 集成测试。
- `cli-cheatsheet`：常用 Kafka CLI 命令。
- `failure-simulation`：模拟 broker 下线、网络延迟、消费者慢处理。

文档重点：

- 单节点适合功能验证，不适合验证副本、ISR、leader 切换。
- 本地测试要尽量复用生产关键配置，例如 acks、retries、isolation、SASL/SSL。
- 对需要时间、网络和 broker 状态的行为，用集成测试而非纯 mock。
- 每个任务都应说明 “如何确认结果正确”。

## 6. 常见问题到任务的映射

| 问题 | 主要任务 | 关键策略 |
| --- | --- | --- |
| 消息重复或丢失 | `04-delivery-semantics`、`07-idempotency-dedup` | 至少一次、手动提交、业务幂等、事务 |
| 外部 DB 与 offset 不一致 | `04-delivery-semantics` | DB 事务 + offset 外部存储，或业务幂等 + 成功后提交 |
| 消费跟不上生产 | `05-rate-limit-backpressure`、`06-lag-rebalance` | 限流、pause/resume、扩容、批处理、下游保护 |
| consumer lag 高 | `06-lag-rebalance`、`10-monitoring-ops` | lag 计算、分区扩容、处理耗时定位 |
| rebalance 频繁 | `06-lag-rebalance` | 静态成员、合理心跳/会话参数、缩短阻塞处理 |
| broker 故障丢数据 | `08-durability-retention` | 多副本、acks=all、min.insync.replicas、ISR 监控 |
| 高吞吐与低延迟冲突 | `09-throughput-latency` | batch、linger、compression、partition 并行度 |
| SASL/SSL 连接失败 | `12-security-acl-quota` | 证书链、机制、用户名密码、NTP、ACL |
| 本地无法复现生产问题 | `13-local-debug-testing` | 多 broker compose、相同客户端配置、故障模拟 |

## 7. Java Kafka 配置与 Sarama 配置映射

| Kafka/Java 常见配置 | Sarama 配置方向 | 说明 |
| --- | --- | --- |
| `bootstrap.servers` | `[]string` brokers 参数 | 传给 `NewClient`、`NewSyncProducer`、`NewConsumerGroup` 等构造函数 |
| `client.id` | `Config.ClientID` | 建议每个模块设置稳定值，方便日志、配额和审计 |
| `acks` | `Config.Producer.RequiredAcks` | `WaitForAll` 接近 `acks=all` |
| `retries` | `Config.Producer.Retry.Max` | 与重试退避配合使用 |
| `retry.backoff.ms` | `Config.Producer.Retry.Backoff` | Go 中是 `time.Duration` |
| `linger.ms` | `Config.Producer.Flush.Frequency` | 批量等待时间 |
| `batch.size` | `Config.Producer.Flush.Bytes` / `Flush.Messages` | Sarama 按字节、条数、频率等触发 flush |
| `compression.type` | `Config.Producer.Compression` | gzip/snappy/lz4/zstd 等取决于构建与 broker 支持 |
| `enable.idempotence` | `Config.Producer.Idempotent` | 还需满足版本、acks、in-flight 等限制 |
| `transactional.id` | `Config.Producer.Transaction.ID` | 用于事务生产者 |
| `group.id` | `NewConsumerGroup` 的 groupID 参数 | 不在 `Config` 里单独设置 |
| `enable.auto.commit` | `Config.Consumer.Offsets.AutoCommit.Enable` | 手动提交时关闭或谨慎使用 |
| `auto.commit.interval.ms` | `Config.Consumer.Offsets.AutoCommit.Interval` | 自动提交间隔 |
| `auto.offset.reset` | `Config.Consumer.Offsets.Initial` | `OffsetOldest` / `OffsetNewest` |
| `isolation.level` | `Config.Consumer.IsolationLevel` | `ReadUncommitted` / `ReadCommitted` |
| `session.timeout.ms` | `Config.Consumer.Group.Session.Timeout` | 影响故障检测与 rebalance |
| `heartbeat.interval.ms` | `Config.Consumer.Group.Heartbeat.Interval` | 应小于 session timeout |
| `max.poll.interval.ms` | `Config.Consumer.Group.Rebalance.Timeout` 等近似项 | Sarama 模型不同，需结合 handler 处理时长理解 |
| `partition.assignment.strategy` | `Config.Consumer.Group.Rebalance.GroupStrategies` | range、roundrobin、sticky 等策略视版本支持 |
| `group.instance.id` | `Config.Consumer.Group.InstanceId` | 静态成员 |
| `fetch.max.bytes` | `Config.Consumer.Fetch.Max` | 拉取大小上限 |
| `fetch.min.bytes` | `Config.Consumer.Fetch.Min` | 最小拉取字节 |
| `fetch.max.wait.ms` | `Config.Consumer.MaxWaitTime` | broker 等待更多数据的时间 |
| SASL/SSL 配置 | `Config.Net.SASL.*`、`Config.Net.TLS.*` | 认证、加密、证书加载 |

## 8. Sarama 可直接实现与外部依赖边界

Sarama 适合直接实现：

- topic 创建、删除、描述、配置读取与部分修改。
- 同步/异步 producer。
- consumer group、partition consumer、offset 提交。
- 幂等 producer、事务 producer 与 read committed 消费。
- 读取 topic/partition 元数据、leader、replica、ISR。
- 读取 consumer group offset 并计算 lag。
- SASL/SSL 客户端连接。
- 使用 mocks 做客户端边界测试。

更适合文档说明或外部工具实现：

- Kafka Connect 的 connector 生命周期管理和数据同步能力。
- Kafka Streams 的状态流处理 API。
- Flink/Spark 的窗口、状态和 checkpoint 语义。
- Broker/JVM 层 GC、磁盘、网络、请求队列监控。
- Cruise Control 风格的自动分区迁移、leader balance、容量均衡。
- 企业级 ACL/审计/配额管理平台。
- Schema Registry 的完整治理流程。
